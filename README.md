# iOSFakeRunning

基于虚拟定位的 iOS 虚拟跑步（Windows）

![](./docs/main_windows.png)

> 本仓库是 [Mythologyli/iOSFakeRun](https://github.com/Mythologyli/iOSFakeRun)（原作者 Myth，LGPL-2.1）的**二次开发版本**，
> 在其基础上补充了真实感模拟、按距离跑步、Apple 设备服务自管理等能力，并修掉了若干会导致闪退与失联的缺陷。

## 二次开发新增内容

### 1. 真实跑步模拟

设备端能接收的只有经纬度，所以"真实感"全部落在**每秒一个坐标点的序列形状**上。

| 项目 | 上游行为 | 本版本 |
| --- | --- | --- |
| 速度 | 整个跑步过程恒定不变 | 恒定配速，或 **N 级速度阶梯**：每级可配速度与持续秒数，只切换相邻一级（往返 ping-pong，不允许跨级） |
| 加减速 | 无，瞬间启停 | 起跑从 0 平滑加速、结束平滑减速；全程纵向加速度受**最大加速度**约束（默认 1.5 m/s²，接近真实跑者） |
| 速度微波动 | 无 | 可选 ±3% 的均值回归（Ornstein-Uhlenbeck）漂移，让配速不是一条直线 |
| 轨迹 | 顶点间直线连接，硬拐角 | 按弧长重采样 + 转角平滑，消除硬拐角与"之字形"轨迹 |
| 定位漂移 | 无，永远在理想路径上 | **路径波动**：垂直于运动方向漂移（默认幅度 1.5 m），保持 1~2 分钟后平滑回到原路径，全程无坐标跳变 |
| 定位噪声 | 无 | 可选高斯噪声（默认 σ = 1.5 m），贴近民用 GPS 误差量级。注意噪声越大，"坐标串实测速度"就越高于设定值（σ = 1.5 m 时 < 2%，σ = 10 m 时可达 2 倍）——这是噪声本身的物理后果，不是缺陷，需要时可配合上文的**速度校准** |
| 循环衔接 | 每圈都直线跳回起点 | 非闭合路线自动**往返跑**（每隔一圈反向），轨迹连续无瞬移 |

### 2. 按跑步距离

除原有"按圈数"外新增**按距离**模式：

- 输入目标距离（如 5.00 km）→ 跑满自动停下；
- 也可同时输入目标用时（如 30 min）→ 反推出配速并按此执行，即"5 公里 30 分钟"；
- 界面实时显示**已跑距离 / 当前配速 / 平均配速 / 用时 / 圈数**（上游完全没有距离显示）。

另外修正了配速不准的问题：上游按"起终点直线距离"分段却实际沿折线跑完全程，导致**实际配速永远快于设定值**（上游 issue #34：设 3.6 m/s 实测约 5.6 m/s）。本版本按弧长参数化并统一时间基准，实测配速与设定值偏差在 2% 以内。

**设备侧读数**：状态栏的"设备侧"一项，是把**真正发给手机的坐标串**逐点算地面距离再除以移动时间得到的配速，
也就是手机（以及手机上任何跑步 App）会显示的那个数字。它和"平均配速"是两条独立算出来的链路——
前者看坐标串，后者看模型内部弧长。两者平时应该基本一致，不一致就说明真实感参数开得太猛了。

**速度校准**（0.50 ~ 2.00，默认 1.00）：手机 App 报的配速和设定对不上时，用它整体缩放所有目标速度。
它**只在你自定速度（恒定速度 / 速度阶梯）时生效**，"目标用时"不接受校准——那是一个"多久跑完"的承诺，
缩放它会直接破坏这个承诺（这一点有回归检查盯着）。默认设置下不需要动它：噪声造成的偏差本身就在 2% 以内。

### 3. Apple 设备服务自管理

程序会在**启动时确保** Apple 设备通信服务在运行，并在**退出时先重置定位、再停止**该服务（"设备"页签有开关，默认开启）。

无需管理员权限。新版 Apple Devices（Microsoft Store 版）**没有 Windows 服务**，而是用户态的
`AppleMobileDeviceLauncher.exe` 监管 `AppleMobileDeviceProcess.exe`（即 usbmux，监听 `127.0.0.1:27015`），
本程序直接管理这两个进程。几点实现上的事实，都是实测得出的：

+ 打包应用**不能按绝对路径启动**（会报"拒绝访问"），也不能通过执行别名或 agent 的 AUMID 拉起；
  唯一有效的办法是激活包的主应用 AUMID，因此启动服务时 Apple Devices 窗口会短暂出现，
  **mux 端口就绪后程序会自动把该窗口关掉**（实测约 8 秒，且关掉 UI 不影响服务本身）。
+ 包信息从注册表 `HKCU\...\AppModel\Repository\Packages` 读取。`C:\Program Files\WindowsApps`
  对普通用户**不可枚举**，所以不能靠列目录来发现包。
+ 若服务本来就在运行，程序不会去动它；退出时按开关决定是否停止。

### 4. 地图视图

左栏的**地图**页签会把**规划路线**（蓝）与**实际发出的轨迹**画在同一张真实底图上。
可拖动平移、滚轮缩放、一键"适配"路线；跑步时红点带航向箭头实时跟随，手动拖动后自动取消跟随。
轨迹画的是真正发给设备的那串坐标，所以"路径漂移""GPS 噪声"这些真实感参数的影响能直接看出来。

地图条带上的两行分别是视图控件（底图 / 适配 / 跟随 / 缩放）和图例（规划路线 / 实际轨迹 / 偏离 / 清除轨迹）。
条带用 `WrapPanel` 而不是分居左右两个角：两块内容都是按内容自适应宽度，窗口缩到最小尺寸时并排放不下，
**换行总好过互相重叠**。每块自身也压在最小窗口的可用宽度以内——地块在最小窗口下只有约 325 DIP 宽，
比它宽的块不会被换行、只会被地图边框**裁掉**，这一条是实测出来的，不是推算的。

**轨迹按圈配色**（六色一循环），因为这个工具最常见的跑法就是同一条小路线绕十几圈；
单一颜色会让整条轨迹反复压在自己身上，把唯一值得看的东西——每圈的差别——盖掉。
循环意味着第 7 圈和第 1 圈同色，这是一次跑步通常不超过六圈时的取舍。

**偏离读数**显示"当前坐标离路线上理想位置多远"和"本次最大偏离"。它是训练真实感参数的唯一反馈信号：
默认设置（漂移 1.5 m + GPS 噪声 σ = 1.5 m）下，跑 4 km 的最大偏离实测约 **5 m**——偶尔甩出几米是真实
GPS 的正常表现，但如果常态就是二三十米，说明漂移或噪声调得过猛了。这个数是从**实际发出的坐标**量出来的，
不是从参数反推的，所以它和地图上看到的橙线永远是同一个事实。

**换路线会清掉轨迹**：轨迹是针对当时显示的那条路线跑出来的，路线一换，两者之间的关系就不成立了，
继续画等于在断言一个不存在的关系。勾选/取消 WGS-84 同样算路线变化（蓝线会平移数百米）。
切底图、缩放、平移**不清**——那些是显示动作，轨迹存的是设备真实坐标，不受影响。

**编辑坐标时地图不会闪没**：文本在逐字符编辑的中途必然存在解析不了的瞬间。早先的实现会让整个地图
（含底图）一起变空，只剩一行提示；现在改为**保留上一条成功的路线**，把问题写在左下角的状态行里并标红。
清空输入框则视为"确实要清除"，地图跟着回到空态。

底图可切换四种，都是实测能直连、**不需要 API key** 的：

| 底图 | 坐标系 | 实测延迟 | 说明 |
| --- | --- | --- | --- |
| 高德矢量 | GCJ-02 | ~0.4 s | 中文街道图，默认 |
| 高德卫星 | GCJ-02 | ~0.4 s | 卫星影像 + 透明路网注记叠加层 |
| Esri 卫星 | WGS-84 | ~1.5 s | 全球影像 |
| Esri 街道 | WGS-84 | ~2.0 s | 国际街道图 |

**坐标系是这里唯一真正的坑。** 高德底图使用 GCJ-02（火星坐标），而程序内部与发给设备的都是 WGS-84。
在杭州一带两者相差 **527 米** —— 不做转换直接把轨迹画上去，整条路线会落到错误的街区。
因此 `CoordinateUtils` 在原有 BD-09 → WGS-84 之外补了 `Wgs84ToGcj02`，按图源坐标系自动转换；
Esri 系列是 WGS-84，不做转换。离线 harness 里有对应回归检查，包括一条
"偏移量必须处于数百米量级"的断言，防止有人随手删掉转换逻辑。

**一个贯穿全局的约定**：路线、轨迹、当前位置在内部**一律是 WGS-84**，只在投影到屏幕的那一刻按当前
底图的基准转换。否则一旦换底图，已经记录下来的数据就要全部重算，而且再也分不清它当初是哪个基准。
这条约定让"换底图"退化成一个纯粹的显示动作，与数据完全解耦。

**磁盘占用**：瓦片缓存在 `%LOCALAPPDATA%\iOSFakeRun\MapCache`，**不在程序目录里**，所以不会把 `dist` 撑大。
缓存上限 **192 MB**，超出后自动删除最旧的瓦片（单块约 20~90 KB，卫星注记层最贵）。
"设备"页签可以看到当前占用并一键清空；清掉只会让下次浏览重新下载。已缓存的区域断网也能显示。

### 5. 顺带修掉的缺陷

| 缺陷 | 后果 | 修复 |
| --- | --- | --- |
| `RunThreadLogic` 数组越界 | 路径点较密（200~300 点）时，点"开始跑步"直接闪退（issue #33） | 重写路径处理，无越界路径 |
| 每发一个坐标都重新握手 lockdown 服务且从不释放 | **曾经以为**是每秒泄漏一个服务句柄、跑几千点后失联，于是改成"服务只建立一次并复用"——**这个判断是错的，改完反而彻底跑不动**（见下一行）。上游那种"每个坐标一条新连接"不是缺陷而是设备要求的语义，缺的只是用完之后要关闭 | 保持"一个坐标一条连接"，但在每条连接用完（或开出一条新的）时把它关掉，既不违反设备语义也不泄漏 |
| `double.Parse` 未指定 culture | 小数点使用逗号的系统区域设置下必然解析失败（issue #1 / #24） | 全程使用 `InvariantCulture`，并同时兼容字符串与数值型坐标 |
| `ResumeRun` 再次 `new Thread` | 反复暂停/继续会叠加线程，进程卡死 | 单一 `RunController` 持有线程 + 取消令牌，暂停/停止立即响应 |
| 挂载失败只提示"挂载失败" | 无法判断是缺镜像、锁屏还是镜像不匹配 | 分别给出具体原因，并列出当前可用镜像版本 |
| **GPS 噪声按采样点独立重抽** | 白噪声让相邻坐标各抖一次，把轨迹长度撑大：设定 2 m/s，手机实测 3.29 m/s（1.65 倍），2 km 跑出 3304 m。**这是"速度总比设定快"的真正原因** | 噪声改成时间相关的漂移（复用已有的 Ornstein-Uhlenbeck 过程），实测降到 1.02 倍 |
| 功能开关关掉后参数仍可编辑 | 路径漂移 / GPS 噪声 / 速度波动三个开关下方共 6 个参数框依然亮着，而同页的"速度阶梯"却正确置灰——同一个程序两套行为 | 统一成一个 `BindSection`，靠容器的 `IsEnabled` 连带禁用子控件，顺带删掉两处逐控件改 `Opacity` 的手写逻辑 |
| **三个"配速方式"单选按钮不在同一个父容器里** | WPF 按**直接父容器**分组单选按钮，而这三个各自带着内联提示、中间还夹着它们管辖的参数面板，于是分属三个组——**可以同时选中恒定速度 + 目标用时 + 速度阶梯**。三个面板一起亮着，真正生效的是哪一个由代码里的隐含优先级决定 | 三个都加 `GroupName="SpeedSource"`（"按圈数/按距离"同理加 `GroupName="RunMode"`），不再依赖视觉嵌套关系 |
| **跑步途中路线文本框仍可编辑** | 路线是跑步参数，但它不在被禁用的设置页签里。跑动中改一个字，地图视野会被"重新适配"拽走，蓝线还会被换成另一条路线，橙线继续往新蓝线上叠，两条线彻底对不上 | 文本框与 WGS-84 开关一并随 `SetRunState` 禁用 |
| 解析失败会把整个地图清空 | 逐字符编辑的途中必然存在解析不了的瞬间，整块地图（含底图）连同蓝线一起变空，只剩一行提示 | 解析失败时保留上一条成功的路线，只在左下角状态行标红报错；清空输入框才视为真的清除 |
| 轨迹只有"开始跑步"能清 | 没有手动清除的入口，而跑完保留轨迹是刻意的 | 地图条带加"清除轨迹"，与轨迹、读数一起清 |
| "跟随"不会自动恢复 | 上一次跑的时候拖过地图，跟随就一直关着；下一次点开始跑步它还是关的，红点默默跑出视野 | 开始跑步时重置为跟随 |
| **定位服务连接被复用** | 本版本一度"优化"成连接时开一次定位服务、之后一直复用它——**这是错的**。实测（iPhone 6 / iOS 12.5，与原版 A/B 对照）：设备收下一条坐标后就关闭那条连接，所以第二个坐标的写入其实是写进了一条已死的连接（TCP 层仍返回成功），第三个坐标的 `service_send` 撞在死连接上**空转**——既不完成也不报错，从外面也无法打断。后果是整个程序僵死：跑线程不再发布状态、点"停止"永远不会被看到（循环回不到检查标志的地方）、连关窗口都会卡在退出时的重置定位上，只能强杀进程。上游之所以没踩到，是因为它**每个坐标都新开一条连接**——那次看着像句柄泄漏，其实是设备要求的语义，我当初把它当成缺陷改掉了，方向反了 | 每次写入开一条**自己的**连接、只发一条消息、随即关闭（`LocationSession.Write`）。既满足"一条连接一条消息"的设备要求，又不留下上游那种每坐标一个句柄的泄漏。另外给每次写入加了 **5 秒截止**作为兜底：万一还有别的路径卡住，跑步会在 5 秒内干净中断并给出提示，界面、"停止"和"退出"都保持可用 |
| **连接成功后闲置一阵，开跑约 5 秒即报"定位服务已无响应"**（且提示错误地把原因写成"手机锁屏"） | 这是紧随上一条修复之后暴露的**下一层问题**。5 秒正是单次写入的截止时间——第一次写入就卡满。根因：本机 usbmux 是 Store 版 Apple Devices 的两个用户进程，**会悄悄消失**（实测手机插着、整套栈死掉、27015 无监听）；手机侧的 lockdown 会话也会单方面回收。任何一种死亡之后，程序手里"连接成功"时建的句柄全部指向死连接，第一次写入就撞上死连接空转。上游同病，只是没有截止时间，表现为**永久卡死**（即老用户熟知的"跑几千点后失联"），而单次失败即判死还把提示归因到没发生的锁屏上 | 三层防御：① `LocationSession` 写入失败后**自动重建设备句柄**（必要时重新拉起 Apple 设备栈）再试一次，废弃句柄按"可能仍被卡死线程占用"处理——只泄漏不释放（释放=use-after-free），并以 8 次为上限防止线程堆积；② 跑步循环给 **90 秒重试窗口**（`LocationRetryWindowSeconds`），期间状态栏显示"定位重试中"，模型原地站立（等同暂停），自愈成功跑步无感继续；③ 放弃时按实际失败阶段给文案（栈未运行/未发现设备/会话失效/服务拒绝写入），附"重新插拔数据线 → 重新检测 → 重启程序"的分级指引，**删除锁屏归因**（实测 iPhone 6 全程未锁屏照样复现） |
| **长跑时内存涨到 17 GB+ 并很快卡死** | 两个叠加来源，都实测确认：① `TileStore._ready` 已解码瓦片内存字典**只进不出**——192 MB 上限只管磁盘缓存，解码后的位图（256 KB/张，非托管内存）没有任何淘汰路径，缩放/换源/长跑跟随平移不断制造新键，17 GB ≈ 66,000 张；② 每次渲染（跟随模式每秒 ≥1 次）对 6 个轨迹调色板槽**各全量重建 StreamGeometry**、路线每帧全量重投影，GCJ-02 底图下每点 ToScreen 都分配新 `double[]`——每秒数 MB 垃圾，GC/终结器长期高压 | ① `_ready` 改为 LRU 缓存，条数上限 1024（≈256 MB），命中刷新访问时间，插入超限淘汰最久未用；② 路线与轨迹点的投影结果**按点缓存**（zoom-0 世界坐标，记录所属图源世代，换源/改线时批量重算），渲染只做"乘 2^zoom + 平移"的线性映射，每帧零堆分配；缩放/平移压力实测内存稳定在 ~210 MB 不再上涨 |
| **点"停止"后 UI 卡死（永远停在"正在停止..."，按钮全灰）** | `LocationSession.Write` 的一把锁罩住了"尝试(5s) → 重建句柄 → 再试(5s)"全程，其中**重建句柄在持锁线程上直接调用工厂**，工厂里的 `lockdownd_client_new_with_handshake` 没有任何超时——连接异常时永久挂起，跑步线程死在锁内，`OnRunFinished` 永远不来。同理，重置定位/退出在 UI 线程同步走这条链（最坏冻结一分钟，握手挂起时永久冻结），连接按钮的握手也在 UI 线程裸调 | 写入链**全部有界化**：① 重建句柄的工厂调用包 45 秒 deadline 线程（超时按废弃计数，与卡死写入同等待遇）；② `BuildDeviceHandles` 与连接按钮的握手各包 15 秒 deadline（超时报"无法与手机建立会话（超时）"）；③ 重置定位改后台线程执行（按钮期间禁用，UI 不冻结）；④ 退出时的定位复位在后台线程跑，UI 最多等 10 秒，超时提示"手机可能仍停留在模拟位置"后照常关窗 |

## 使用方法

### 运行本版本

```bash
# 需要 .NET 6.0 SDK 或更高（本机已有 6.0.428 / 8.0.420）
dotnet build
dotnet run --project iOSFakeRun
```

`DeveloperDiskImage` 文件夹放在仓库根目录即可：程序会从当前目录及可执行文件所在目录**逐级向上查找**，
所以无论从 `bin/` 里运行还是从仓库根目录运行都能找到镜像。

### 原有使用步骤

+ 如果你的电脑不具有 .NET 6.0 环境，请在 [此处](https://dotnet.microsoft.com/en-us/download/dotnet/6.0) 下载并安装 .NET Desktop Runtime 6.0
+ 虚拟定位需要开发者镜像。本仓库**不附带**镜像文件（体积太大），需要自行获取：
  iOS 14 ~ 16.7 的镜像请从 [Mythologyli/DeveloperDiskImage](https://github.com/Mythologyli/DeveloperDiskImage)
  下载对应版本（也可用其 CI 产物），放入程序目录下的 `DeveloperDiskImage/<版本号>/`；
  低于 iOS 14 的版本请执行以下步骤:
    + 进入 [DeveloperDiskImage](https://github.com/Mythologyli/DeveloperDiskImage) 仓库
    + 查看自己的 iOS 版本，下载对应的 DeveloperDiskImage.dmg 和 DeveloperDiskImage.dmg.signature
    + 进入 iOS Fake Run 软件文件夹。在 DeveloperDiskImage 文件夹中建立以版本号为名称的文件夹（如 13.7），将刚才下载的两个文件放入此文件夹

  如果你的 iOS 为 16，请执行以下步骤:
    + 进入设置 > 隐私与安全性
    + 打开开发者模式开关

+ 打开[路径拾取网站](https://fakerun.myth.cx)。通过点击地图构造路径。点击时无需考虑间距，会自动用直线连接。路径点击完成后，单击上方的路径坐标——复制，将坐标数据复制到剪贴板
+ 打开 iOS Fake Run 软件，将坐标数据粘贴到左侧的文本输入框中
+ 将 iOS 设备连接至电脑并解除设备锁屏。你需要确保电脑上的相关驱动正确（安装 iTunes 或 Apple Devices 即可）
+ 点击连接按钮将 iOS 设备连接到软件，然后在右侧"跑步"页签选择按圈数或按距离，点击开始跑步
+ 跑步结束后，点击重置定位恢复 iOS 设备的正常定位，否则设备在重启前将保持在虚拟定位上

### 构建发布版

要生成免安装的发布目录（`dist\`，可直接双击其中的 exe 运行）：

```bash
dotnet publish iOSFakeRun/iOSFakeRun.csproj -c Release -o dist
```

`route.save` 与 `error.log` 属于运行期产物，会写在首次找到它们的位置（当前工作目录或仓库根目录），
均不入库、随用随生成。

> **坐标系提示**：路径拾取网站给出的是百度 BD-09 坐标，程序默认会转换成 WGS-84。
> 如果你直接粘贴 GPX 或国际地图的坐标（已是 WGS-84），请勾选左栏文本框下方那个"坐标已经是 WGS-84"选项，
> 否则会整体偏移数百米。

### 离线验证

`tools/RunHarness` 是不需要连接手机即可运行的验证工具，直接驱动运行引擎检查配速、距离、加速度上限、
轨迹连续性等性质：

```bash
dotnet run --project tools/RunHarness
```

当前覆盖 29 项检查：配速/距离/加速度等运行引擎性质、上游"配速偏高"缺陷的回归项、Apple 设备组件的定位，
以及地图用到的坐标转换与 Web Mercator 投影（含与实际在线瓦片索引的一致性校验）。
其中三项是**实时驱动 RunController** 的（其余检查都是全速驱动引擎模型）：用假 sink 按剧本失败，
验证短暂失联能在重试窗口内自愈跑完、持续失联会在窗口耗尽后如实报失败、恢复期间模型原地站立且状态持续发布。

其中"发给设备的坐标串，实测速度等于设定速度"这一项值得单独说：它不看模型内部的弧长，
而是把真正发给设备的坐标串逐点算地面距离再求速度——手机和任何跑步 App 就是这么测的。
模型自洽并不等于设备侧测出来是对的，这两条链路必须分别验。
它按**应用出厂默认设置**（漂移开、速度波动开、σ = 1.5 m）逐个速度跑一遍并要求偏差 < 5%；
剩下的噪声倍数只作为信息打印，因为**噪声拉大之后坐标串测出来就是更长**，这是模型的正确行为而不是缺陷
（σ = 10 m、设定 1.5 m/s 时实测 3.02 m/s，2.01 倍）——"速度校准"这个窗口存在的意义就是这种情况。

"速度校准系数按比例缩放实测速度，且不影响目标用时"则是把上面那条规则钉死：
校准 0.50 / 1.00 / 1.50 时实测速度必须正好成比例，而目标用时 1000 s 的跑步在同样校准下必须仍然约 1000 s 结束。

"偏离读数与坐标串的真实偏离一致"把地图上那个偏离数字钉在地上：真实感全关时必须恒为 0；
只开漂移时最大值必须跟着漂移幅度走（1.5 m → 约 1.67 m，4.0 m → 约 4.45 m）；
再叠上噪声时必须严格更宽、且仍在噪声量级内。它防的是"这个数从参数反推出来、自己跟自己一致"——
那样它就无法充当参数的检验手段了。

## 已知边界

+ **只能模拟位置**。`com.apple.dt.simulatelocation` 协议的载荷只有经纬度，因此**高程、心率、步频/步数无法模拟**。
  这也是 HealthKit 步数与定位距离在同一台设备上互相矛盾的根本原因，不是本程序能绕过的。
+ **自带开发者镜像最高到 iOS 16.7**。iOS 17 起 Apple 改用按设备签名的 Personalized DDI，旧的挂载方式失效，
  需要改走 CoreDevice / RSD 隧道（`pymobiledevice3` 那一套），属于另一个量级的改动。
+ 目标框架仍为 `net6.0-windows`（上游设定）。构建时有该框架已停止支持的提示，功能不受影响。
+ **定位服务是"一条连接只收一条消息"的。** 这一点是实测出来的：设备收下一条坐标后就关闭连接，
  所以任何复用连接的做法都会在第二个坐标上撞死（细节见上面的缺陷表）。这个协议原本是给 Xcode
  "模拟单个位置"用的，不是为连续跑配速设计的——程序能用是因为它严格按这个语义，一次一条连接。
+ **比"一条连接一条消息"更底层的问题：连接会整条整条地悄悄死。** 本机 usbmux 不是 Windows 服务，
  而是 Store 版 Apple Devices 的用户进程（`AppleMobileDeviceLauncher` 监督 `AppleMobileDeviceProcess`，
  监听 127.0.0.1:27015）；实测这套栈会在无人操作时整个消失（手机插着、端口无人监听），手机侧的
  lockdown 会话也会单方面回收。死掉之后程序手里的句柄全部指向死连接，对死连接的任何调用都是
  空转而不是报错——这才是"开跑约 5 秒失联"与"跑几千点后失联"的共同根源（一个有截止兜底所以报错，
  一个没有截止所以卡死）。因此每次写入失败都会先经工厂重建句柄（含重新拉起 Apple 栈）再重试一次，
  跑步循环另有 90 秒重试窗口兜底；拔插数据线仍是最后的恢复手段，因为 mux 有时会错过设备的
  到达事件（实测：栈活着、USB 枚举正常，mux 仍报 0 设备，重新插拔后才恢复）。
+ **本程序固定使用软件渲染**（`App.xaml.cs` 里 `RenderOptions.ProcessRenderMode = SoftwareOnly`）。
  开发期间实测这台机器的 WPF 硬件渲染管线会进入坏状态：所有 WPF 应用（包括上游原版）客户区
  整片白/黑，UIA 元素树却活着，事件日志无报错；给注册表 `HKCU\Software\Microsoft\Avalon.Graphics`
  加 `DisableHWAcceleration=1` 后原版立刻渲染正常，坐实是 GPU/合成路径的问题而非程序问题。
  本程序的视觉负载（几十张 256px 瓦片 + 几条折线，每秒失效一两次）软件渲染绰绰有余，
  顺带获得对坏驱动状态的免疫力。如果你的其他 WPF 应用也出现"白窗口但程序没死"，
  重启电脑或重装显卡驱动吧——那是机器的问题。
+ 每次写入都带 5 秒截止作为兜底：设备库在死连接上的发送会空转且无法打断，截止能让跑步干净中断
  而不是把窗口冻住。真出现超时，**那个卡在库里的线程收不回来**（会占一个核，对应句柄只能泄漏），
  累计 8 次后写入会快速失败并提示重启程序；重试窗口与句柄重建就是为了让这种情况尽量不发生。
+ 退出时停止 Apple 设备服务会一并结束后台的 Apple 设备进程；如果你同时在使用 Apple Devices 的同步功能，
  可以关闭"设备"页签里的开关。
+ **窗口最小尺寸为 800×520**。再窄下去两栏都会被挤到不可读，所以设了下限；底部状态栏在空间不足时
  会自动换行而不是截断，两栏宽度则始终按比例伸缩。
+ **地图底图的服务条款**：高德的两个栅格端点无需 key 即可访问，但它是未公开的内部接口，不是给第三方用的正式 API，
  存在被限流或变更的可能。Esri 的是公开服务。本程序仅缓存瓦片、不修改内容；如果你的使用场景需要合规保证，
  请自行替换为天地图等有正式授权（需申请 key）的图源 —— 在 `FakeRun/MapTiles.cs` 的 `MapTileSources.All` 里加一项即可，
  天地图是 WGS-84，连坐标转换都不用动。
